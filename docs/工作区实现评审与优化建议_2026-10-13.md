## 一、口径与门禁：系统仍然不完全会说真话

> 对应实施路径 §一"第一原则"。这一类问题不解决，后面所有分数都不可信。

### A1 ⛔ Gate 漏判结构问题（已实测证实）

**现象**：

```
TRIGGER/00_TRIGGER.sql | L2 score=20.0  passed=False
                        | pglast total=21 failed=0
                        | structure_issues=12
                        | gate=True  gate_failures=[]
```

**根因**：`workspace/verification/framework.py:533-536`

```python
elif lv.level == "L2" and config.gate_fail_on_parse_error:
    failed = lv.details.get("pglast", {}).get("failed", 0)
    if failed:
        fails.append(f"L2 有 {failed} 条语句解析失败")
```

只看 `pglast.failed`。而 `syntax_check.check_structure()` 产出的 `block_mismatch`（`severity="critical"`）**只参与 `score_syntax` 扣分，不进 Gate**。结果：结构崩掉的文件分数腰斩，Gate 却放行。

**影响**：DoD-2/DoD-3 都建立在 Gate 之上；Gate 漏判，验收结论就漏判。

**建议**（不改代码，仅方案）：Gate 增加 `structure_issues` 非空即失败，或至少 critical 级失败。

### A2 ⛔ DoD-2 / DoD-7 两个硬门禁都不在 Gate 里

| 门禁 | 实现位置 | 是否在 Gate 路径 | 证据 |
|---|---|---|---|
| DoD-2 残留 | `verification/residuals.py` + `scripts/scan_oracle_residuals.py` | ❌ **独立 CLI** | `verify_oracle_poc_output.py` 未 import residuals |
| DoD-7 完整性 | `converter/integrity.py` | ⚠️ 只在 `convert_oracle_poc.py:482-496` 生效 | verify 脚本完全不感知 |

**后果**：`convert_oracle_poc.py` 可以在产物仍有 **74 处 major 残留**的情况下 `exit 0`；而 `verify_oracle_poc_output.py` 可以在产物有静默丢失的情况下报"Gate 通过"。

**这正是实施路径 §1.3 描述的老毛病换了个位置**：原来是"转换报告假成功"，现在是"验证报告不完整但看起来是全绿的"。

**建议**：确立**单一验收入口**（见 F1）。

### A3 跳过即免责——DoD-4 事实上永不验收

`framework.py:521-525`：

```python
for lv in levels:
    if lv.skipped:
        continue
```

L4 被跳过时，`gate_require_cases` / `min_case_coverage`（§84、§89）这两个专门为"没验证到就不算通过"设计的开关**完全不生效**。

叠加 `verify_oracle_poc_output.py:110` 的 `cases=[]`，形成闭环：

```
cases=[]  →  L4 skipped("未提供用例库")  →  gate 直接 continue  →  DoD-4 永远"不失败"
```

同样的机制让 `--no-pg` 下的 L3 安装失败、L3.5 首调冒烟全部免疫。

**建议**：为"因配置缺失而跳过"与"因环境不可用而跳过"区分语义；后者应判 Gate 失败或至少在报告中标红。

### A4 分数口径不可比，且仓库内自相矛盾

| 位置 | 总分 | L3 | L3.5 | L4 |
|---|---|---|---|---|

### B5 ⛔ 完整性断言在最后一次改写之前计算

`convert_oracle_poc.py` 的执行顺序：

## 三、分层与依赖方向

### C1 ⛔ 引擎反向依赖 AST 层，与 §3.2 架构决策冲突

`ora2pg_py_perlstyle/perlstyle_engine.py:3636-3644`：

```python
_repo_root = Path(__file__).resolve().parent.parent
_parsers_dir = _repo_root / "workspace" / "parsers"
if str(_parsers_dir) not in _sys.path:
    _sys.path.insert(0, str(_parsers_dir))
from chunker_ast import chunk_oracle_by_antlr
```

实施路径 §3.2 的核心设计是「**AST 层和 Agent 层都不在主路径上**」「AST 是事后体检，不改产物」。而现在：

- 引擎在**函数内部动态改 `sys.path`**，直接依赖 `workspace/parsers/`；
- 意味着 AST 切块**已经在转换主路径上**（不只是体检）；
- `workspace/parsers/` 一旦移动/删除，引擎会静默降级到正则 chunker——**而正则 chunker 正是 P4-2f 要根治的"丢 3 个顶层函数"根因**。

依赖方向应当是「引擎不依赖 AST，AST 依赖引擎产物」。当前是反的，且反向依赖失败时**不报错**。

### D5 补充：缺"依赖完整性"层的具体后果

迁移手册 §22.1 L4 层定义为「调用目标、表、视图、类型、序列是否存在」，§28.1 列为风险「Package 调用指向不存在的函数」。

当前 PACKAGE_BODY 转换产出的是 schema + 一堆函数，**函数之间的调用引用是否有悬空，没有任何检查**。手册 §22.4 把"未解析依赖"与"对象缺失"并列为**阻塞发布**——而 DoD-7 只覆盖了后者。

## 七、需要你决策的三个问题

1. **F2 的 golden cases 可信度怎么定级？**
   该文件 `note` 明确写着"期望值由源码语义推导，**非 Oracle 实例实测**"。手册 §22.4 要求语义不确定须标 `MANUAL_REVIEW`。如果 65 条期望值全部降级为"待人工复核"，DoD-4（L4 100%）就仍然无法闭环——**是否安排一次 Oracle 实例回归**？（这是当前 DoD-4 唯一真正的阻塞项，不是代码问题。）

2. **`parsers/plsql/` 与 `pipeline/` 的归属？**
   两者都是"0 处生产引用的 AST/grammar 副本"。`pipeline/` 已标注冻结，`parsers/plsql/` 未标注且带一整套 visitor。是否按冻结处理，或直接废弃？

3. **P5-1 是否重新估算？**
   实施路径估 2–3 天"扩写 ≥30 条用例"，但已有 65 条资产。实际工作量集中在接线（F2，约 0.5 天）+ 期望值可信度复核。**是否把 P5-1 缩减为"接线 + 定级"，把用例扩写推到二期？**
