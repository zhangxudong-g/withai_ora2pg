## 二、技术栈评估

### 2.1 规则引擎 —— 主力，快速通道

**现状**：6195 行、94 个函数、11 个转换入口。实测单文件 **4.7 毫秒**。

**能力边界**：

| 能力 | 现状 |
|---|---|
| 机械替换（`NVL`→`COALESCE` 等）| ✅ 主力 |
| 多对象文件拆分 | ❌ `convert_trigger` 只转第一个 |
| 占位符回填校验 | ❌ 无 `_assert_no_unresolved_placeholders` |
| 嵌套子程序提升 | ⚠️ `_lift_nested_subprograms` 已实现，但覆盖不全 |
| 外连接拓扑重写 | ❌ 按表名局部决策，产生 `ON TRUE` 笛卡尔积 |

**定位**：**保持主力，不搬迁**。6195 行资产已被生产脚本硬编码引用，搬迁风险大于收益。

### 2.2 ANTLR AST —— 体检仪，不做翻译

**实测结果**：

| 检验项 | 结果 |
|---|---|
| 运行时 / 生成版本 | **4.13.2，精确匹配** |
| TRIGGER 解析 | 6 语句，**0 错误**，6/6 对象名正确提取 |
| FUNCTION / PROCEDURE 解析 | **0 错误** |
| PACKAGE_BODY 解析 | 4389 节点，**8 错误** |

**那 8 个错误的根因**：`PACKAGE_BODY:161` 嵌套函数缺 `DECLARE` 关键字（Oracle 允许嵌套函数直接跟在 `BEGIN` 后，ANTLR 社区 grammar 要求 `declareBlock`），**同一根因连锁 8 条**。

**决定性代价**：

| 场景 | 耗时 | 倍率 |
|---|---|---|
| 规则引擎转一个触发器文件 | **4.7 ms** | 1× |
| ANTLR 解析同一文件 | **11,700 ms** | **约 2500×** |

**架构决策**：**ANTLR 做"看医生"，不做"动手术"** ——
不进转换主路径（2500 倍减速不可接受），只做**独立结构体检器**，转换完后跑一次（约 48s）。

**它能看见正则永远看不见的东西**：

| 问题 | 正则 | AST |
|---|---|---|
| 源 6 个触发器、产物 1 个 | ❌ 无"应该有多少"概念 | ✅ 数 `Unit_statementContext` |
| 嵌套子程序被压平成注释 | ❌ 只看到 `/* TODO */` 文本 | ✅ 树里有 `Trigger_block` 且深度异常 |
| `%TYPE` 引用哪张表哪列 | ⚠️ 靠正则猜 | ✅ 直接读 `AttributeContext` |
| 函数是否被替换成桩 | ❌ 看签名像就信 | ✅ 树里有没有真实 body |

### 2.3 AI Agent —— 复杂体最后一公里

**适用范围**：嵌套子程序语义保持、28 处 TODO 桩二次翻译、BULK COLLECT / UTL_FILE / 自治事务。

**护栏（缺一不可）**：
1. `validate_pg` 硬校验（pglast + L3 试装），不过必留 TODO
2. 每批前 git commit 产物快照，可回滚
3. 配额上限 200 次，超限转人工
4. **SPEC 桩必须 `RAISE EXCEPTION 'not implemented'`**，禁止静默返回 NULL

### 3.2 三层协作关系

```
     Oracle 源文件

  │  问：源里有几个对象？产物里有几个？         │
  │      有没有被压平的嵌套子程序？              │
  └───────────────────────────────────────────┘
          │ 若结构异常
          ▼
  ┌───────────────────────────────────────────┐
  │  【Agent 层】agent/（按需，限量）           │  ← 复杂体最后手段

          ▼

  └───────────────────────────────────────────┘
```

**关键设计**：AST 层和 Agent 层**都不在主路径上**。
AST 是"事后体检"（转换完跑一次），Agent 是"按需救火"（只在 AST 判定异常时介入）。
这样日常转换速度不受影响，同时获得全局可验证性。

### 3.3 grammar 副本的冗余决策

**决策（2026-10-09 已执行）**：ANTLR 生成物复制到 `workspace/parsers/grammar/`，**允许冗余**。

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 复制到 workspace** ✅ | workspace 自包含；不依赖冻结目录；可独立演进 | 8.75MB 冗余 |
| B. 只读引用 `pipeline/` | 无冗余 | workspace 不自包含；清理 pipeline 即断链 |

**理由**：① 自包含性优先——生产实现目录不应依赖已冻结目录；
② 冻结不等于断链——若 workspace 依赖 `pipeline/`，将来清理它会打断 AST 层；
③ 冗余换稳定——8.75MB 换确定性划算。

**落地情况**：6 个文件共 **8,754,421 B**，SHA-256 与来源**全部一致**；
独立解析验证通过（只把 workspace 副本入 `sys.path`，TRIGGER 得 6 unit / 0 err）。

**版本管理**：原始 `pipeline/parsers/grammar/` 的 6 个文件本就在 git 跟踪内，
副本沿用同一策略，**无需引入 LFS**。

> **红线**：两份并存时**以 `workspace/parsers/grammar/` 为准**；
> `pipeline/parsers/grammar/` 仅作历史追溯，不再更新。

**关键约束**（详见 `workspace/parsers/grammar/README.md`）：
1. **禁止手工编辑生成物** —— 要改行为改 `workspace/parsers/*.py` 上层代码
2. **runtime 必须严格 4.13.2** —— 升级前必须先跑解析冒烟
3. **`.g4` 源不在仓库，无法重新生成** —— 可维护性缺口，P5-3 需处理
4. **PACKAGE_BODY 嵌套函数缺 `DECLARE`** → 需在 `structure_check.py` 预处理或区域降级

### v3.7 P4-2 回归修复（2026-10-13 10:33 手动全链路实测发现）

> **优先级高于 v3.1~v3.6 的全部任务。** 编号建议 **P4-2R**，归入 P4-2 收尾。

**现象**：DoD-1 一键安装在 `FUNCTION/00_FUNCTION.sql:78` 失败（`语法错误 在 ";" 或附近的`），
后续 5 个文件未跑。L3 安装 **成功 151 / 243，失败 92**。

**根因**：嵌套函数 lift 路径拼装产物时，函数体末尾多输出一个分号：

```sql
EXCEPTION
    WHEN OTHERS THEN RETURN NULL;
    END ;;          ← 正确应为 END;
$$;
```

**归因（实测）**：92 个失败中 **73 个（79.3%）** 的对象含 `END ;;`。

**回归证据**：

| 版本 | FUNCTION 文件 `END ;;` 数 |
|---|---|
| `f52a1ba`（P4-2c）| **0** |
| `ce4f630`（P4-2e，启用 lift）| **8** |
| `2810905`（P4-2h，当前）| **42** |

**定位**：`END <name>;`→`END;` 的剥离逻辑在 `perlstyle_engine.py:4154-4160`，
但 **lift 走另一条拼接路径**，需顺 `_lift_nested_subprograms` 的产物拼装处定位。
复现：`convert --clean` 后 `grep -n 'END\s*;;' oracle_poc/output/*/*.sql`。

**同步附带发现**：

| # | 发现 | 数量 | 归属 |
|---|---|---|---|
| N1 | `WHEN OTHERS THEN RETURN NULL` 静默吞错（§13.1 加粗禁止）| **13**（`WHEN OTHERS` 总计 104）| **P2-5c** |
| N2 | 嵌套函数声明原样留在 `BEGIN` 块内未 lift，**但注释已标「提升为独立函数」** | 3 | **P4-2R** |

> **N2 是"假成功"的又一实例**：注释与事实不符。
> 与 §1.3 描述的根因同源——**注释不能作为"已处理"的证据**。

**⚠️ 基线口径订正**：

> 本次是**第一次 PG 连通状态下的完整验证**。此前 HANDOFF 记录的 84.1 / 81.6 等分数
> **均为 `--no-pg` 降级数据（L3/L3.5/L4 全跳过，65% 权重缺席）**。
> **P4-2R 修复后：L3 失败 92 → 8（独立）+ 7 依赖连锁；`END ;;` 73→0；单测 257 / 残留 78（无新残留）。
> _verification_* 报告未重跑，分数待 W0 一并刷新。**

### v3.8 P4-2R 修复完成（2026-10-13，commit `541f1dc`）

**根因定位**：`perlstyle_engine.py:3916` `_lift_nested_subprograms` 把 Oracle 嵌套函数
`END <name>;` 替换为 `r"\1;\2"`，在 END 后强制加分号 + 保留原 `\2` 中的分号 → `END ;;`。

**修复**：regex 改为 `r"^(\s*)END\s+NAME\s*;?\s*$"` + 替换为 `r"\1END;"`，代码变更 +4/-2 行。

**验收**（PG 15 实测）：
- `END ;;` 73→0
- L3 失败 92→8（**剩余 8 个属 P4-3 复杂体**：`RETURNS TABLE(IN SYS_REFCURSOR)` /
  `FOR rec IN (SELECT...)` 游标循环 / 依赖关系链）

- 残留 78→78（无新残留）
