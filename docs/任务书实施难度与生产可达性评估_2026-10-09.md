## 一、总体结论（一句话先看）

**任务书的范围合理，但存在"任务书预估工作量偏乐观 + 部分目标不可达生产级别"的问题。** 在 20 个工作日（任务书 §四 W1–W3 排期）内，T1–T14 大概率可以让产物达到"**功能等价 + 可一键安装**"的工程交付级；但距离**生产级别**（高可用、严密边界、完备回归、可维护性、Oracle 语义 100% 对齐）还有 3 项**结构性硬伤**——主要是 PG 8.4 环境约束 + Oracle 专有能力无对等物 + 转换器本体有未量化债务。

下面分三部分展开：
- §二 实施难度评估（每个 T 的真实工时和风险）
- §三 任务书本身的薄弱点（被低估的环节）
- §四 "生产级别"的定义与差距

## 二、任务书 T1–T15 真实难度评估

### 2.1 工时复盘（任务书预估 vs 真实评估）

| 任务 | 任务书预估 | 真实评估 | 偏差 | 关键依据 |
|---|---|---|---|---|
| **T1** 扫描器 | 0.5 天 | 1–1.5 天 | **+1 天** | 16 模式 × 白名单 + Gate 接入 + 误报收集 |
| **T2** L3.5 冒烟 | 1 天 | 2–3 天 | **+1.5 天** | 28 个 FUNCTION + 12 个 PKG 成员 + 6 个 TYPE method 各自 fixture，teardown 链复杂 |
| **T3** %SUBQUERY | 0.5–1 天 | 1–2 天 | **+0.5 天** | 链式引用 + 还原后子查询本身需重过 smoke |
| **T4** (+) JOIN | 1–2 天 | **3–5 天** | **+2 天** | 这是**难度最高**的规则任务，Kahn 算法在 4+ 表上容易出环；当前 outer_join.py 只有 175 行"标记"代码，**完全是新写** |
| **T5** %TYPE | 1 天 | 1.5–2 天 | **+0.5 天** | schema 字典 + 类型映射 + 三段式 + 参数回溯；TYPE/PACKAGE_BODY 跨文件引用要兜底 |
| **T6** SYNONYM/SEQ | 0.5–1 天 | 1–1.5 天 | **+0.5 天** | 序列同义词引用点替换涉及全产物 grep |
| **T7** ANTLR 装 | 0.5 + 1 排障 | 1–3 天 | **+0.5 天** | ANTLR 版本匹配 + 本语料覆盖率实测 + 失败段落降级方案都要做 |
| **T8** TRIGGER AST | 1 天 | 2–3 天 | **+1.5 天** | 5 个丢失触发器要补，**其中复合触发器和 INSTEAD OF 在 PG 8.4 无原生对等**；拆解+多触发器协作的语义保真度需 smoke 反复验证 |
| **T9** TYPE 重设计 | 2–3 天 | **5–8 天** | **+4 天** | 这是**仅次于 T11 的硬骨头**：8 个类型全部重写 + 16 个函数 + 下游 PACKAGE_BODY 联动改数组惯用法（极多点位）；`CONFIG_LIST` 数组嵌数组需业务决策；跨文件命名冲突 |
| **T10** 禁内联 | 1–2 天 | 2–3 天 | **+1 天** | lift 实现是文本级配对深嵌套；命名冲突（CALC_AVG / VALIDATE_FILTER 与包内同名）+ 父函数局部变量引用检测要枚举 |
| **T11** Agent 回灌 | 3–5 天 | **5–10 天** | **+4 天** | **关键路径上最大不确定性**：28 个 TODO × 3 轮 retry × 失败列入人工清单 = 单 Agent 调用 30–80 次是乐观估计；实际会遇到 Agent 把正确代码改错、需要回滚、validate_pg 误杀等 |
| **T12** 专项件 | 2–4 天 | **3–6 天** | **+2 天** | BULK COLLECT/PIPE ROW 各新建 200 行规则；UTL_FILE 业务决策卡住就**全部阻塞**；FUNC_SETLOG 自治事务需 superuser/dblink |

| **T14** 端到端 | 0.5 天 | 1–2 天 | **+1 天** | 失败重试循环 + 报告生成 + DoD-6 mtime 检查 |
| **T15** 防复发 | 1 天 | 1–2 天 | **+0.5 天** | golden 样例 + CI + 文档 |
| **合计** | **20 天** | **30–50 天** | **+50% 到 +150%** | — |

**结论**：任务书 §四 "W1–W3 (20 天) 排期"是**乐观场景**。真实工期 **30–50 天**（约 1.5–2.5 倍），单人全栈；多人并行可压缩到 25–35 天。

### 2.2 任务书"难度低估"的根因

任务书普遍按"单点修复"估时，**低估了三件事**：
1. **回归测试 + 跨文件联动**——T9 改 TYPE 同时要改 PACKAGE_BODY 引用，T10 lift 嵌套函数同时要处理命名冲突。任务书说"涉及文件"列了 3 个，实际改动 5–8 个。
2. **决策阻塞**——T6/T8/T12 都有"业务决策项"，任务书默认"决策很快"，实际业务方响应时间不可控。
3. **环境/依赖排障**——T7 ANTLR 装版本可能 1 天就过去，T2 L3.5 装 PG 沙箱可能折腾半天。任务书"Pre-1 到 Pre-7"列了 7 条但**没有为每条预留排障时间**。

## 三、任务书本身的薄弱点

任务书在以下几处过于乐观或含糊，实施时**必须重新评估**：

### 3.1 T4（(+) JOIN）被低估为 M–L（1–2 天）

`pipeline/rules/outer_join.py` 当前只有 175 行**标记规则**（detect + add warning），完全没有 `convert()` 实现。要做的工作：
- 写完整的 AST/语法树分析（FROM 列表 + WHERE 子句拆解）
- 写图论算法（节点 = 表别名，边 = 等值条件 + (+) 方向标记）
- 写拓扑排序（Kahn 算法 + 环检测）
- 写 ANSI JOIN 链渲染（含 ON 条件归属、外连接方向）
- 7 个 golden 样例 + 单测

**这是**一个**小型编译器子任务**，1–2 天**根本写不完也测不完**。预估 3–5 天更现实。

### 3.2 T9（TYPE 重设计）联动范围被低估

任务书说"联动 PACKAGE_BODY 改数组惯用法"，但**没量化**：
- PACKAGE_BODY 28 个实现中，**估计 10+ 个**会用到 `t_score.FIRST` / `t_score.EXTEND` / `t_score.COUNT` 等集合属性
- 每次改都得 smoke 验，**单是联动就 1–2 天**
- 加上 8 个类型重写 + 16 个函数 + 10 个 golden 样例 = 5–8 天

**建议**：把 T9 拆成 T9a (核心类型) + T9b (联动) + T9c (SELF method 改造)。

### 3.3 T11（Agent 回灌）的不确定性

任务书说"30–80 次 Agent 调用 × Stage3 工具链调用 3–5 步"，这是**乐观估计**。实际遇到的典型场景：
- Agent 把"正确的 TODO 桩代码"改错（"过度转换"）
- Agent 输出 plpgsql 语法错但 pglast 通过（动态 SQL 部分）
- Agent 输出语义对但包内调用名拼错
- 28 个 TODO 里有 5–8 个是**根本转不了的**（PIPELINE、UTL_FILE、自治事务），这些**进人工清单**而不是"批量回灌"

**真实工时**：第一遍批量跑 = 2 天；逐个修 Agent 错误输出 = 2–3 天；业务决策项阻塞 = 1–2 天等待。**5–10 天是正常估计**。

### 3.4 任务书忽略的隐藏债务

任务书**没有显式列出**以下问题，但实施时一定会撞上：

1. **命名冲突**（T10 lift 后与包内函数同名）：`CALC_AVG`、`VALIDATE_FILTER` 等在 FUNCTION 提升 + PACKAGE_BODY 内**各有一份**。需要统一命名空间 + alias 机制——任务书提了"加 `_lifted` 后缀"但没给具体方案。
2. **跨文件依赖排序**（T8/T9/T10）：改 TYPE 必然要改 PACKAGE_BODY 引用，改 FUNCTION 必然要改 PACKAGE_BODY 调用——任务书的依赖图是**粗粒度**（T7→T8/T9），实际**细粒度**的依赖要每个文件单独画。
3. **测试数据对齐**（T13）：49 条 TEST_DATA 是给**当前**产物设计的；T8/T9 重建后，触发器行为和类型结构变了，TEST_DATA 必须**同时改**，否则 L4 全失败。
4. **oracle_poc 之外的回归**（T15）：gkb 语料（真实项目）目前能跑通 oracle_poc 修复的规则；T3/T4/T5/T6/T10 改了之后**一定会影响 gkb**，任务书说"双跑"但**没预留回归时间**。

### 3.5 任务书没有处理"定义不充分"的任务

以下任务的"完成"是**主观的**，没有客观验收点：

- **T8 INSTEAD OF 触发器**（TRG_V_STUDENT_IO）：任务书说"需视图可更新化"——是改成 `INSTEAD OF` 触发器？还是改视图为可更新视图？还是改应用层 SQL？这是**业务决策**，任务书没明确。
- **T9 数组嵌数组拍平**（CONFIG_LIST）：jsonb vs 分隔符 vs 改 schema——这是**架构决策**，任务书只说"待业务确认"。
- **T12 自治事务**（FUNC_SETLOG）：dblink vs 拆独立 PROCEDURE vs 改架构——任务书说"默认 dblink"，但 dblink 要 superuser，**默认就错了**。

**建议**：任务书应把每个"决策项"显式列进 §七 外部资源需求，并标注**默认决策**和**阻塞时长**。

## 四、"生产级别"的定义与差距

### 4.1 生产级别的 5 个维度

| 维度 | 含义 | 任务书 DoD 覆盖？ |
|---|---|---|
| **D1 安装性** | 一键部署 0 错误 | DoD-1 ✅ |
| **D2 功能等价** | 输入/输出语义一致 | DoD-4 ✅ |
| **D3 运行稳定性** | 边界/并发/资源/异常路径全部正确 | ⚠️ **部分**——任务书只测"典型输入"，未测边界和并发 |
| **D4 可维护性** | 转换逻辑清晰、命名规范、文档齐全 | ⚠️ **部分**——T15 防复发工程化是"骨架"，缺细节 |
| **D5 可观测性** | 错误信息、链路追踪、性能指标 | ❌ **任务书未涉及** |

### 4.2 即使 T1–T15 全部完成，仍达不到生产级别的 5 个原因

#### ① PG 8.4 环境约束（**最关键的硬伤**）

任务书全篇围绕 PG 8.4 写，但 PG 8.4 缺失多项**生产必需**的能力：
- `plpgsql` 不支持 `COMMIT`/`ROLLBACK`（11+ 才有）→ FUNC_SETLOG、SP_PROCESS_SCORE、TRG_STUDENT_AU **无解**
- 没有 `PIPE ROW` 的原生替代（必须整体重写为 `RETURNS SETOF`）→ 2 个 PIPELINE 函数 **架构级重写**
- 存储过程**不支持显式游标声明** → SP_CALC_RANK、SP_GEN_SCORE_REPORT **必须改函数或重写**
- 复合触发器**无对等概念** → TRG_SCORE_COMPOUND **必须拆+测试语义保真**

**结论**：任务书在 PG 8.4 上能做到 **"功能等价 + 可安装"**，但**这本身就不算生产级**。**生产级**至少要 PG 11+（事务控制）甚至 PG 13+（增强的错误处理）。

#### ② Oracle 专有能力在 PG 端的"等价物"代价大

- `BULK COLLECT / FORALL` → 改写为 `INSERT...SELECT` 或 `FOREACH`（语义不同：前者批量，后者循环；性能特征完全不同）
- `PRAGMA AUTONOMOUS_TRANSACTION` → dblink 或拆独立 PROCEDURE（架构改动）
- `UTL_FILE` → 应用层导出或 `file_fdw`（安全审批/性能）
- `REF CURSOR` → PG 端 `OPEN FOR` 但**没有客户端游标缓存**（需要应用层重写）

这些**不是"修"出来的，是"重新设计"出来的**。任务书把它们当"修复"，低估了工作量。

#### ③ 转换器本体有未量化的债务

当前 `ora2pg_py_perlstyle/perlstyle_engine.py` 是 6000+ 行的规则引擎，**没有完整单测覆盖**。T3/T4/T5/T6/T10 改完后：
- 短期：oracle_poc 通过 L1–L4
- 中期：gkb 真实项目跑，**预计会发现 20–50 个新问题**（占位符协议、命名冲突、跨 schema 引用、字符编码……）
- 长期：**这是 oracle_poc 第 6 版修复**，前面 5 版的债务没还

任务书 T15 防复发工程化是**必要但不充分**——只覆盖 oracle_poc + gkb 两个语料，**真实项目场景远不止**。

#### ④ 任务书不涉及"运维级别"事项

生产级别还需要：
- **回滚方案**：转换失败如何回退到原 Oracle？
- **数据迁移**：TEST_DATA 49 条是手写的；真实项目可能是**百万行**——任务书完全没碰
- **性能基线**：转换前/后的 SQL 性能对比、索引重建、统计信息更新
- **审计与合规**：转换产物的可追溯性、原始 SQL 保留

#### ⑤ T11（Agent 路径）的可重复性是软肋

Agent 产出**本质上是非确定性**的：同一条 Oracle 输入，两次跑 Agent 可能产出 2 个不同 PG 输出。任务书要求"validate_pg 硬校验"，但**语义等价校验**远比 pglast 复杂：
- pglast 过了不代表语义对（比如 `BEGIN x = 1; END` —— pglast 过，逻辑反了）
- L3.5 冒烟过了不代表所有输入都对
- 真实数据下可能 1% 路径出错（边界/空值/字符编码）

**结论**：T11 路径在**功能等价**层面可信，在**生产稳定**层面**不可信**。

## 六、建议补充的"生产化二期任务书"

如果目标是**真正生产级别**，任务书**必须**追加以下 T16–T25（任务书**当前没有**这些）：

| 任务 | 主题 | 预估 |
|---|---|---|
| T16 | **PG 版本升级到 13+**（解锁 COMMIT/ROLLBACK、改善错误处理、并行查询） | 1 周（含数据迁移测试） |
| T17 | **dblink 自治事务层**（解决 FUNC_SETLOG、TRG_STUDENT_AU） | 3 天 |
| T18 | **批量数据迁移工具**（百万行级 CSV/管道导入，不是手写 49 条 TEST_DATA） | 1 周 |
| T19 | **性能基线 + 索引重建**（用 pg_stat_statements、EXPLAIN ANALYZE 对比 Oracle） | 1 周 |
| T20 | **完整 L4 业务等价用例库**（≥100 用例，覆盖所有边界/异常/并发） | 2 周 |
| T21 | **Agent 输出确定性化**（固定 prompt 模板 + 多 Agent 投票 + 人工抽检） | 1 周 |
| T22 | **运维级回滚方案**（原 Oracle 实例保留、PG 影子库、灰度切换） | 1 周 |
| T23 | **审计与可追溯**（原始 Oracle 保留、转换日志、字段映射表） | 3 天 |
| T24 | **真实项目回归**（除 oracle_poc + gkb，至少 2 个新语料） | 1 周 |
| T25 | **24×7 稳定性测试**（故障注入、慢查询降级、连接池耗尽） | 1 周 |

**总工期**：约 8–10 周（2 个月）才能真正到生产级别。

## 七、回到用户的问题（直接回答）

### Q1：实现难度如何？

**真实工时是任务书预估的 1.5–2.5 倍**（30–50 天而非 20 天）。原因：
- 4 个 P0 任务（T1/T2/T3/T4/T5）的"单点修复"实际都涉及**跨文件联动 + 回归测试**
- T9 (TYPE 重设计) 和 T11 (Agent 回灌) 实际工时被低估 50%–100%
- 任务书没量化**命名冲突**、**跨文件依赖**、**TEST_DATA 对齐**、**gkb 回归**四项隐藏债务

**主要风险**：
- T11 Agent 路径的非确定性（最大不确定性来源）
- 业务决策项（UTL_FILE、自治事务、数组嵌数组）卡住可阻塞 1–2 周
- PG 8.4 环境约束让 5 个对象**无原生对等**，必须重新设计

### Q2：是否最终可达到生产级别？

**任务书 T1–T15 完成后：可达"工程交付级"，不可达"生产级别"**。

工程交付级（✅ 可达）：
- 一键安装 0 错误（DoD-1）
- 主要功能语义等价（DoD-4，大致）
- 冒烟通过（DoD-3，业务决策项除外）
- Gate 分数 ≥ A（DoD-5）

生产级别（❌ 不可达）：
- **PG 8.4 缺事务控制**——FUNC_SETLOG、SP_PROCESS_SCORE、TRG_STUDENT_AU 等 5+ 个对象**没有原生 PG 8.4 解决方案**
- **Agent 路径非确定性**——同输入多输出，运维不可控
- **运维/可观测/回滚/性能/审计均未涉及**——任务书完全没规划
- **真实数据迁移未涉及**——49 条手写 TEST_DATA ≠ 百万行真实数据
- **回归覆盖不足**——只测 oracle_poc + gkb 两个语料

**如果目标是生产级别**：
1. **先把任务书当前 T1–T15 完成**（30–50 天）作为"工程交付级"基线
