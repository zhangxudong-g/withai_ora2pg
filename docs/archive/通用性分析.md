# Oracle → PostgreSQL 转换工具通用性分析

## 通用化进展

### ✅ 2026-09-16 改进

- **新增 `convert/oracle_pg_rules.py`**: 集中管理所有 L1 通用规则
  - NVL → COALESCE, DECODE → CASE, INSTR → STRPOS
  - SYSDATE → CURRENT_DATE, SYSTIMESTAMP → CURRENT_TIMESTAMP
  - DBMS_OUTPUT, DBMS_UTILITY, DBMS_SQL 处理
  - EXECUTE IMMEDIATE → EXECUTE
  - RAISE_APPLICATION_ERROR → RAISE EXCEPTION (保留错误码)
  - || NULL 语义处理
  - ROWNUM → LIMIT
  - 可通过配置自定义规则

- **新增 `pg.py`**: 统一 CLI 入口 (convert/verify/info 子命令)
  - 支持任意 Oracle 项目 (通过 `PG_SOURCE_BASE` / `PG_FUNC_PREFIX` 环境变量)
  - 一键转换 + 验证

> 注: 早期的 `convert/convert_oracle_to_pg.py` 与 `convert/example_config.yaml` 已删除, 统一由 `pg.py` 接管。

## 概述

当前工具针对 GKB（学籍管理）项目的 Oracle → PostgreSQL 迁移开发。本文分析各组件的通用性。

---

## 通用组件 ✅

### 1. `convert/type_mapping.py` 
**通用性: ★★★★★**

- Oracle → PostgreSQL 类型映射规则
- 纯规则配置，无业务逻辑
- 可直接用于任何 Oracle → PG 迁移项目

### 2. `convert/ddl_converter.py`
**通用性: ★★★★☆**

- 表结构转换（CREATE TABLE, ALTER TABLE）
- 约 90% 通用逻辑
- 小部分针对 GKB 项目特点（如 NVARCHAR2 特殊处理）

### 3. `convert/view_converter.py`
**通用性: ★★★★☆**

- VIEW 基本语法转换
- 移除 Oracle 特有语法（FORCE, HINT, COMMENT）
- `DECODE()` → `CASE WHEN` 转换
- Oracle `(+)` 外连接需手动处理（这是 Oracle 特有的复杂语法）

---

## 部分通用组件 ⚠️

### 4. `convert/plsql_converter.py`
**通用性: ★★★☆☆**

- 独立函数/过程转换
- **通用部分**: 参数声明、RETURN 类型、基本 SQL 转换
- **项目特定部分**: 
  - 包调用桩 (`GAA*PK*.*`)
  - 复杂对象专用策略 (`GKBSKJDOG` 等)

### 5. `convert/convert_package_body.py`
**通用性: ★★☆☆☆**

- PACKAGE_BODY 解析和转换
- **项目特定**:
  - 硬编码源路径 `gkb/01.release/`
  - 函数命名前缀 `gkbpkg_*`
  - 包内自引用处理逻辑

---

## 项目特定组件 ❌

### 6. `convert/pkg_stubs/` 外部包桩
- 包含 `GKAPK*`, `GABPK*` 等包函数声明
- 完全针对 GKB 项目的外部依赖

### 7. `fixtures/testdata/` 和 `fixtures/test/`
- 包含 GKB 业务测试数据和断言
- 需要根据新项目重新编写

### 8. `convert/_complex_section.py`
- 8 个复杂对象的专用策略配置
- 针对 GKB 项目的特殊处理

---

## 转换为通用工具的建议

### 最小改动（推荐）

1. **参数化源路径**
   ```python
   # 当前
   _base = Path('gkb/01.release')
   
   # 建议
   _base = Path(args.source_dir or 'source')
   ```

2. **配置化函数命名前缀**
   ```python
   # 当前
   pg_name = f"gkbpkg_{prefix}_{sname.lower()}"
   
   # 建议
   pg_name = f"{args.prefix}_{prefix}_{sname.lower()}"
   ```

3. **提取包桩配置为独立文件**
   ```
   config/
     ├── type_mapping.yaml    # 类型映射
     ├── stub_packages.yaml   # 外部包桩配置
     └── complex_objects.yaml # 复杂对象策略
   ```

### 新项目使用步骤

```bash
# 1. 准备源文件
mkdir source/{table,function,procedure,view,package_body}

# 2. 复制并修改配置
cp config/type_mapping.yaml myproject_type_mapping.yaml
# 编辑映射规则

# 3. 运行转换
python convert/ddl_converter.py --all --source source/table/
python convert/plsql_converter.py --all --source source/function/
python convert/view_converter.py --all --source source/view/

# 4. 手动处理复杂对象
# 根据错误日志处理 REF CURSOR、嵌套函数等

# 5. 编写项目特定的测试用例
```

## 关键技术差异（可能影响通用性）

| Oracle 特性 | 当前处理 | 通用性影响 |
|------------|---------|-----------|
| `(+)` 外连接 | 标记但不转换 | ⚠️ 需要手动 SQL 重写 |
| `CONNECT BY` | 注释化 | ⚠️ 需要改写为 WITH RECURSIVE |
| `REF CURSOR` | 转为动态 SQL | ✅ 通用处理 |
| `%ROWTYPE` | 部分支持 | ⚠️ 复杂场景需手动 |
| 嵌套函数 | 转为普通函数 | ⚠️ 可能有语义差异 |
| 包 (PACKAGE) | 转为函数簇 | ✅ 通用模式 |
| `SYSDATE` | 转为 `NOW()` | ✅ 通用 |
| `NVL` | 转为 `COALESCE` | ✅ 通用 |

---

## 结论

**可直接用于**：
- 类型映射规则
- 基本 DDL 转换
- 基本 VIEW 转换
- 简单 PL/SQL 函数

**需要适配**：
- 源文件路径
- 函数/表命名规则
- 外部依赖包桩
- 复杂 SQL 逻辑（外连接、递归查询）
- 业务测试用例

**建议**：以当前工具为基础，根据新项目特点修改配置和测试用例，而非重写整个工具链。
