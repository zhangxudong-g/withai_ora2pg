# Oracle → PostgreSQL 迁移实施计划

## 一、建立转换基准与验证框架

1. 整理典型 SQL / PL/SQL 案例。
2. 建立覆盖矩阵：

   * 基础 SQL、复杂嵌套、聚合
   * 日期、字符串、NULL
   * ROWNUM、CONNECT BY
   * 动态 SQL、DBMS_SQL
   * Procedure、Function、Package
3. 为每个案例定义验证方法：

   * 语法与编译验证
   * 执行结果验证
   * 边界条件验证
   * 异常处理验证
   * 数据变更验证
   * 性能验证（必要时）

---

## 二、修复并完善脚本转换引擎

目标：构建**通用、可扩展、可回归测试的基础转换引擎**。

1. 修复现有简单 SQL 转换问题。
2. 改进复杂嵌套 SQL 的处理能力。
3. 将转换规则模块化、分类管理。
4. 增加转换失败和风险识别机制。
5. 为每项修复增加测试案例。
6. 建立自动回归测试。

---

## 三、验证 SQLines 转换能力

1. 使用典型 SQL / PL/SQL 进行 SQLines 转换。
2. 执行统一的验证流程。
3. 记录：

   * 可直接转换的场景
   * 转换错误的场景
   * 语义差异
   * 不支持或需要人工处理的场景
4. 将验证结果整理为转换规则和限制清单。

---

## 四、构建 Agent + Skill 转换方案

### Skill 主要能力

1. 分析 Oracle 源码及依赖关系。
2. 识别 Oracle 特有语法和 API。
3. 检索并应用转换规则。
4. 调用可复用的基础转换脚本。
5. 处理复杂 SQL / PL/SQL 语义转换。
6. 自动生成验证用例。
7. 执行 PostgreSQL 验证。
8. 输出转换结果、风险和未验证项。

**LLM 负责复杂语义分析，脚本负责稳定的基础转换，验证机制负责控制转换质量。**

---

## 五、典型案例 PoC

选择以下案例进行端到端验证：

1. 普通 Function
2. 复杂嵌套 SQL
3. 包含动态 SQL 的 Procedure
4. 包含 `DBMS_SQL` 的 Procedure
5. 包含内部依赖的 Package

比较：

* 原始 Oracle 逻辑
* 脚本转换结果
* SQLines 转换结果
* Agent + Skill 转换结果
* 验证结果和风险

---

## 六、逐步扩展到 GKB 全量迁移

1. 根据 PoC 结果完善规则和 Skill。
2. 按对象类型分批迁移：

   * 表定义
   * 数据
   * Function / Procedure
   * Package
   * Trigger
3. 执行分批验证和回归测试。
4. 记录无法自动转换的内容。
5. 对高风险对象进行人工设计和确认。

### 总体原则

> **先建立验证基准，再完善脚本；以 SQLines 作为参考基线，以 Agent + Skill 处理复杂语义，最终通过 PostgreSQL 验证迁移结果。**
