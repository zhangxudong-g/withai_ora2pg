# 阶段 3：验证 SQLines 转换能力

## 1. 阶段目标

使用阶段 1 建立的统一案例集和验证标准，客观评估 SQLines 对 Oracle → PostgreSQL 迁移的覆盖范围、转换质量和限制。

## 2. 主要任务

### 2.1 明确 SQLines 验证范围

确认：

- 使用的 SQLines 版本
- 支持的输入数据库类型
- 目标数据库类型
- 可使用的命令行参数
- 是否存在对象数量、文件大小或功能限制
- 是否支持 Function、Procedure、Package 和 Trigger
- 是否支持动态 SQL 和系统包

### 2.2 使用统一案例执行转换

对阶段 1 的每个案例执行 SQLines 转换，并保存：

- 原始 Oracle 文件
- SQLines 输出文件
- 执行参数
- 工具版本
- 日志
- 错误和警告
- 转换耗时

不要只选择容易转换的案例，应保留复杂和失败案例。

### 2.3 建立转换结果分类

建议分类：

- A：无需修改即可执行，且行为验证通过
- B：语法基本正确，需要少量人工修改
- C：可以转换结构，但存在语义风险
- D：只能部分转换
- E：无法转换或结果不可用

分类仅用于项目内部管理，并应附带具体证据。

### 2.4 进行静态检查

检查 SQLines 输出是否存在：

- Oracle 专用函数
- Oracle 数据类型
- Oracle 外连接语法
- 未处理的 Package 调用
- 未处理的 DBMS_SQL
- 未处理的动态 SQL
- 不正确的日期表达式
- 不兼容的异常处理
- 不完整的过程或函数结构
- 变量和参数引用错误

### 2.5 进行 PostgreSQL 验证

在 PostgreSQL 环境中执行：

- DDL 创建
- 函数和过程创建
- 基础查询
- DML 操作
- 异常场景
- 事务场景
- 边界数据场景

如果没有 Oracle 数据库，应明确区分：

- 基于 Oracle 语义和文档的理论检查
- PostgreSQL 实际执行检查
- 无法进行的 Oracle 对照验证

不得将理论推断写成已经完成的 Oracle 结果验证。

### 2.6 对比现有脚本和 SQLines

针对每个案例记录：

- 两种方案的输出差异
- 各自成功和失败的部分
- 需要人工修改的内容
- 风险类型
- 维护成本
- 可自动化程度
- 对复杂 PL/SQL 的支持情况

不只比较“是否生成 SQL”，还要比较结果正确性和可维护性。

## 3. 主要产出

- SQLines 转换测试报告
- SQLines 支持矩阵
- SQLines 失败案例清单
- 与现有脚本的差异分析
- 人工修正清单
- 适合自动转换和不适合自动转换的场景说明

## 4. 完成标准

- 所有典型案例使用统一方法完成测试。
- 每个结论都有输入、输出或执行日志作为依据。
- 明确 SQLines 的适用范围和限制。
- 不以语法通过代替业务正确性验证。
