## 逐一分析

### 1. TABLE/001_STUDENT_MST.sql —— 🟢 可直接使用

- **L3**：3/3 安装成功；L1/L2 均 100 分；pglast 顶层解析通过。
- NUMBER→BIGINT、VARCHAR2→VARCHAR 映射正确；主键、索引、COMMENT 保留。
- **瑕疵（不影响执行）**：
  - `REC_*` 审计列由 DATE/TIME 变为 CHAR(23)/CHAR(12)，是刻意的字符串存储约定，但与源类型语义不同，下游若按日期比较需注意；
  - 列定义尾部多余空行、`)` 与 `;` 分离，纯格式问题。
- **结论**：无需修改即可投产。

### 2. SEQUENCE/00_SEQUENCE.sql —— 🟡 可用，需业务复核

- **L3**：6/6 成功；语法零残留。
- **问题**：
  1. 头部自带警告：`SEQ_LOG_ID` 原 MAXVALUE 99999999999999999999 超出 PG bigint 上限，被**静默截断**为 9223372036854775807——容量语义改变（实际影响极小，但应知悉）；
  2. `SEQ_STUDENT_NO` 保留 `CYCLE` + `MAXVALUE 9999999999`，与原 Oracle 一致，但循环回绕策略需业务确认。
- **结论**：可安装可用；两处语义差异需登记复核。

### 3. SYNONYM/00_SYNONYM.sql —— 🟡 可安装，存在隐性风险

- **L3**：11/11 成功（PG 无 SYNONYM，转成 `CREATE OR REPLACE VIEW sm_xxx AS SELECT * FROM xxx`，方案合理且已加注释）。
- **风险**：
  1. `sm_seq_student / sm_seq_jobnum / sm_seq_log` 三个"序列同义词"被转成**视图**。PG 中 `SELECT sm_seq_jobnum.NEXTVAL` 或 `nextval('sm_seq_jobnum')` 都会失败——凡是通过同义词访问序列的代码迁移后必须改写；
  2. 视图别名使可更新性受限（简单视图可 autoupdate，但复杂场景不如同义词透明）。
- **结论**：当前语料中尚无对象经由 SM_* 访问序列，暂不阻塞；作为通用转换产物需在使用规范中标注该限制。

### 4. DATA/00_TEST_DATA.sql —— 🟢 可直接使用

- **L3**：49/49 插入成功；引擎标记 passthrough=true，内容与源逐字节一致（input/output 同为 162 行）。
- INSERT 语句本身即为 PG 兼容写法；末尾 `COMMIT;` 合法。
- **注意**：数据中的 `BIRTH_DATE/ENROLL_DATE/EXAM_DATE` 均为 YYYYMMDD 整数，与 BIGINT 列定义匹配，无冲突。
- **结论**：无需修改。

### 5. TABLE/002_SUBJECT_MST.sql —— 🟡 可安装，含 1 个语义陷阱

- **L3**：8/8 成功。7 张表结构转换正确；`PROCESS_LOG` 中 `SQLCODE/SQLERRM` 只是**列名**，不是 Oracle 残留（L1 在此报 major 属误报，但无害）。
- **问题**：
  1. `TEMP_SCORE_BATCH` 生成 `CREATE TEMPORARY TABLE ... ON COMMIT PRESERVE ROWS`。PG 只支持 `ON COMMIT DROP | PRESERVE ROWS | DELETE ROWS`，其中 **PRESERVE ROWS 是默认行为、书写合法**，故能安装；但 Oracle 全局临时表(GTT)"跨会话共享结构、每次会话独立数据"的语义在 PG temp 表中并不等价（PG temp 表仅创建者会话可见、会话结束即销毁）。批次处理若依赖 GTT 跨连接共享，会出功能性问题；
  2. 日期类字段同样落为 CHAR(23)/BIGINT，与 001 相同的类型约定问题。
- **结论**：可安装；TEMP 表使用方式需人工确认后再定是否改造。

### 6. TYPE/001_TYPES.sql —— 🔴 不可直接使用（能装不能算）

- **L3**：16/16 安装"成功"，但 L2 报告 2 条语句级问题（85 分），且安装成功≠可用。
- **致命缺陷（静态确证）**：
  1. 对象类型方法被"提升"为独立函数，如 `GET_STATUS_of_SCORE_RECORD()`，其函数体引用 `SELF_SCORE_RECORD_IS_PASS`、`SELF_STUDENT_RECORD_BIRTH_DATE` 等**根本未声明的标识符**。plpgsql 允许带 `RETURNS REFCURSOR`/无参形式安装，但**一旦调用必然报"column/variable does not exist"**；
  2. 这些函数全部**没有 SELF/入参**（`()` 空参数列表），逻辑上无法工作；
  3. `TABLE OF` 集合被转成复合类型 `(items SCORE_RECORD[])`，而后续包体代码仍按 Oracle 集合方式写 `tLIST.EXTEND; tLIST(nCOUNT) := ...`，两者互不兼容；
  4. `REF_CURSOR_T` 对象类型退化成单列复合类型 `(CURSOR_NAME VARCHAR(100))`，语义完全丢失；
  5. `A_CONS_PRM AS (items VARCHAR(1000)[])` 数组嵌数组在 PG 不受支持（可能安装侥幸，使用必错）。
- **结论**：必须由人工/AI 重写为 PG 原生 domain/composite/array 用法后方可使用。

### 7. TRIGGER/00_TRIGGER.sql —— 🔴 不可直接使用（潜伏运行期炸弹）

- **L3**：2/2 安装成功（函数+触发器都建上了）。
- **致命缺陷**：函数体 DECLARE 段残留
  `vMAX_STUDENT_NO STUDENT_MST.STUDENT_NO%TYPE;`
  PG 无 `%TYPE`。plpgsql 在 CREATE FUNCTION 时不解析变量类型（延迟到首次执行），所以**安装成功纯属侥幸**；任何一次 INSERT INTO STUDENT_MST 都会在触发器执行时报 `type "student_mst.student_no%type" does not exist`，**整个插入链路瘫痪**。
- 其余逻辑（MAX+1 取号、TO_CHAR 时间戳、DEFAULT 补值）翻译质量尚可。
- **结论**：一行改动即可修复（`%TYPE`→`BIGINT`），但按本次要求不做修复，判定不可直接使用。

### 8. VIEW/00_VIEW.sql —— 🔴 不可直接使用

- **L3**：6/7，`V_STUDENT_SCORE` 安装失败：`ERROR 42P01 对于表"t",丢失FROM子句项`。
- **根因（对照源文确证）**：源为 Oracle `(+)` 老式外连接四表笛卡尔写法。转换器把 `SB.TEACHER_CD = T.TEACHER_CD(+)` 挪进了 SUBJECT_MST 的 JOIN ON 子句（此时 T 尚未引入），并把 TEACHER_MST 变成 `LEFT JOIN ... ON TRUE`，同时**删除了 S↔SC、SB↔SC 两条关键连接条件**：
  - 引用 T 早于其出现 → 语法层面即失败；
  - 即便强行修正引用顺序，缺失的连接条件会把 INNER 语义退化为 CROSS JOIN，**结果集行数爆炸、业务含义全变**。
- 另外 6 个视图（V_STUDENT_STATS/V_SCORE_RANK/V_SUBJECT_STATS/V_TEACHER_STATS/V_DEPENDENCY_GRAPH/V_STUDENT_WITH_SCORE）转换良好：窗口函数、NULLIF、PERCENT_RANK、CUME_DIST、ROUND(::NUMERIC) 等均正确。
- L1 还提示存在 1 处 `IS NOT NULL\n\n\n;` 式的列级约束残留片段。
- **结论**：V_STUDENT_SCORE 必须人工重写 ANSI JOIN；其余 6 个视图基本可用，但该文件整体不可直接使用。

### 9. PACKAGE/00_PACKAGE.sql —— 🟡 可安装，但全是空壳桩

- **L3**：13/13 成功。Package→Schema（`CREATE SCHEMA PKG_SCORE_MANAGE`）+ 12 个声明提取，架构策略正确。
- **关键事实**：12 个过程/函数体全部是 `BEGIN -- TODO: implement [RETURN NULL;] END;` **占位桩**。它能安装是为了给 PACKAGE_BODY 的前向引用兜底，本身无任何业务行为。
- **风险**：若 BODY 文件安装失败（实际正是如此），外部调用会**静默命中空桩返回 NULL/-0**，比直接报错更危险；且 BODY 中私有成员（FUNC_SETLOG 等）不在 SPEC 中，桩覆盖不全。
- **结论**：作为"接口骨架"可用；作为交付物不可用，必须以 BODY 的真实实现为前提。

### 10. PROCEDURE/00_PROCEDURE.sql —— 🔴 不可直接使用

- **L3**：5 个中仅 1 个安装成功（SP_PROCESS_SCORE ✅，其余 4 个 ❌）。
- **逐对象分析**：
  - `SP_PROCESS_SCORE`：唯一完整可用者。OUT 参数转 INOUT 可编译安装；但注意两点隐患：a) 体内 `ROLLBACK` 出现在 EXCEPTION 分支——PG 过程异常块进入时事务已 aborted，ROLLBACK 会被忽略/告警，错误码语义靠 o_nRTN 勉强保住；b) `MERGE` 无关，逻辑直译质量较好。
  - `SP_GEN_SCORE_REPORT` ❌：`CURSOR CUR_STUDENT FOR ...` 声明残留 + `EXIT WHEN CUR_STUDENT%NOTFOUND` + `R_STUDENT CUR_STUDENT;`（Oracle 记录型变量），PG 语法错误（"语法错误在 FOR"）。
  - `SP_BATCH_IMPORT_SCORE` ❌：`BULK COLLECT INTO` ×3、`FORALL i IN 1..list.COUNT`、`v_student_list.COUNT`、`SQL%ROWCOUNT`、`SQLERRM` 全残留；更严重的是 MERGE 的 USING 子句被替换成 **`USING(%SUBQUERY0%)` 内部占位符未回填**——即使手工清掉 FORALL，这条 SQL 也是坏的。
  - `SP_CALC_RANK` ❌：显式游标 + `FOR R IN CUR_STUDENT LOOP` 非法组合 + **两处 `%SUBQUERY0%/%SUBQUERY1%` 占位符未展开**（排名计数子查询整体丢失）。
  - `SP_BATCH_DELETE_SCORE` ❌：BULK COLLECT + FORALL DELETE + SQL%ROWCOUNT。
- **结论**：4/5 不可安装，且存在子查询丢失这类"即使能装也不等价"的深层缺陷。

### 11. FUNCTION/00_FUNCTION.sql —— 🔴 不可直接使用（结构性损坏）

- **L3**：16 个中 9 个安装成功；L2 仅 20 分；文件头 20+ 条引擎自白警告（"Nested FUNCTION … skipping lift / Inlined … may change behavior"）。
- **系统性缺陷——嵌套子程序"内联"产生的坏代码**（本文件 5 处，PACKAGE_BODY 另有 3 处）：
  形如
  ```
  g_vSQL : IS NULL; /* INLINED: BUILD_SQL() */
  ```
  这是把 `g_vSQL := BUILD_SQL(...)` 的内联改写成了**语法上不成立的碎片**；同类还有 `o_nVALUE : IS NULL;`、`v_sql : IS NULL;`、`nTOTAL_SCORE : IS NULL;`、`v_LINE : IS NULL;`。
- **逐对象要点**：
  - `F_GET_TOTAL_SCORE`：`EXECUTE IMMEDIATE`（应为 EXECUTE）、`BUILD_SQL(...) /* TODO: complex body */` 占位、END 标签错位（BEGIN=1/END=3）——侥幸安装成功，**运行必错**。
  - `F_GET_AVG_SCORE` ❌：体内混入孤儿 `END ADD_COND;`、引用未声明变量 `i_vSQL`（PG 报 `"i_vsql" 不是一个已知变量`）。
  - `F_GET_GRADE_LEVEL`：调用未定义的 `GET_THRESHOLD/DETERMINE_LEVEL`（lift 失败留下 TODO 占位）——安装成功但调用即 `function does not exist`。
  - `F_CALC_RANK` ❌：`END BUILD_FULL_SQL;` 孤儿标签 + 缺表达式。
  - `F_GET_STUDENT_LIST_PIPELINE` ❌：Oracle PIPELINED 范式原样保留——`RETURNS STUDENT_LIST`（应为 `RETURNS SETOF`）、裸 `RETURN;`、`PIPE ROW(STUDENT_RECORD(...))`、`v_cursor%NOTFOUND/%ISOPEN`。PG 根本无法安装。
  - `CALC_AVG / CALC_RANK / VALIDATE_FILTER / GET_SUBJECT_NAME / FORMAT_CONTENT / F_GET_JOBNUM`：lift 出的独立函数，多数形态正确（这是本文件里可用的部分）。
  - `F_GET_SCORE_LIST_PIPELINE` ❌：同上 PIPE ROW 问题。
  - `F_GET_STUDENT_CURSOR` ❌：内联残骸 + `ADD_COND(v_SQL,...)` 引用未声明 `v_SQL`。
  - `F_GET_WEIGHTED_AVG` ❌：`v_score` 未声明、两段内联循环体互相踩踏、`GET_ALL_SCORES /* TODO */` 悬空。
  - `F_GET_CONFIG_VALUE`：`SYSTEM_CONFIG.CONFIG_VALUE%TYPE` 残留——安装侥幸成功，**调用必炸**（同 TRIGGER 的问题）。
  - `CLEAN_VALUE` ❌：体内出现 `END ;;` 双分号损坏 + 调用未定义的 `TRIM_VALUE`。
- **结论**：该文件是"规则引擎处理嵌套子程序能力不足"的典型样本：能装的函数约半数一调用就死，不能装的占 7 个。必须逐个重写。

### 12. PACKAGE_BODY/00_PACKAGE_BODY.sql —— 🔴 不可直接使用（问题总集成）

- **L3**：28 个中 16 个安装成功；L1 71.4、L2 15，综合 39.2/F。
- **包全局变量 → `set_config/current_setting`**：思路可行，但落地有多处硬伤：
  - `FUNC_INIT` ❌：`BEGIN set_config(...)` ——把赋值语句直接拼进 `BEGIN` 关键字行（应为 `PERFORM`），语法错误；且 `INIT_WSINFO` 是被内联掉的嵌套函数，调用悬空。
  - `PBATCH / P_GEN_REPORT` ❌：同样出现 `BEGIN set_config(...)` 拼接错误；`current_setting(...) := ...` 的伪赋值；`CUR_ALL_STUDENT(i_nGRADE, i_nCLASS_NO)` 游标函数从未定义（SPEC 里没有、BODY 里 lift 失败）。
  - `PROC_INSERT_WORK` ❌：`WHEN OTHERS THEN FUNC_SETLOG(...)` ——PL/SQL 过程调用未加 `PERFORM`；`c_ONLINE` 常量未定义（包常量表未被搬运）。
  - `PROC_BATCH_SCORE_PROCESS` ❌：体内**残留一个完整的 Oracle 嵌套函数** `FETCH_BATCH_DATA(... ) RETURN TEXT[] IS ... END FETCH_BATCH_DATA;`（lift 半途而废）；`BULK COLLECT INTO v_result`、`FORALL`、`v_scores[i].STUDENT_NO`（对 TEXT[] 用记录点号！）、`SQL%ROWCOUNT`、`SQLCODE/SQLERRM`、未定义 `c_OK/c_ERR`。
  - `PROC_BATCH_RANK_UPDATE` ❌：`EXECUTE IMMEDIATE v_sql BULK COLLECT INTO`、`FORALL`、`v_ranks[i].CLASS_RANK`（TEXT[] 元素点号访问）、`v_ranks.COUNT`。
  - `PROC_EXPORT_CSV` ❌：`UTL_FILE.FILE_TYPE / FOPEN / PUT_LINE / FCLOSE / IS_OPEN` 整体保留（PG 无 utl_file 模式，报 `模式"utl_file"不存在`）；又见 `v_LINE : IS NULL; /* INLINED */` 坏赋值；`RETURN rec...` 出现在 FOR 循环体内的孤儿代码。
  - `FUNC_GET_CONFIG` ❌：声明了 `INOUT o_nVALUE`  yet 体内 `RETURN -1;`（PG 禁止"带 OUT 参数的函数返回值"）；内联残骸 `o_nVALUE : IS NULL;`、孤儿 `END CLEAN_NUMERIC;`。
  - `VALIDATE_SCORE_VALUE` ❌：签名被改成 `i_nVALUE INOUT NUMERIC` 却仍 `RETURNS BOOLEAN`（OUT 参数强制结果类型冲突）；体内 `END PROC_LOAD_CONFIG;` 标签与本函数名不符（**函数体与另一函数的结尾串行粘连**，是最典型的切分错误）；`set_config(...)` 裸调用。
  - `F_GET_SCORE_LIST` ❌：`SCORE_LIST();` Oracle 构造器语法、`tLIST.EXTEND`、`tLIST(nCOUNT) :=`、`CUR_ALL_SCORE` 未定义——与 TYPE 文件的集合建模缺陷联动失败。
  - **相对健康（安装成功）的成员**：FUNC_SETLOG（但体内 `COMMIT` 位于 plpgsql 函数中——PG 函数禁止事务控制，**调用时才报错**；AUTONOMOUS_TRANSACTION 仅留注释未解决；`FORMAT_MESSAGE` 已被内联掉但仍被调用）、FUNC_FORMAT_DATE、FUNC_GET_GRADE_LEVEL（GET_THRESHOLD 悬空 TODO）、FUNC_CALC_TOTAL/AVG（`EXECUTE IMMEDIATE` 未转 `EXECUTE`，调用即错）、PROC_CLEAR_WORKTABLE、P_PROCESS_SCORE、P_BATCH_PROCESS_SCORE、P_BATCH_UPDATE_RANK、P_EXPORT_CSV、F_GET_TOTAL/AVG/RANK（转发壳，`current_setting('...g_nPASS_SCORE')` 直接与数值比较存在 text vs numeric 隐式转换风险，且未配置时 current_setting 抛 undefined_object）。
- **结论**：即使 16/28 安装成功，绝大多数也在**首次调用时**才暴露错误；该文件是全项目风险最高点。

### 13. 00_CREATE_ALL_PG.sql（一键安装入口）—— 🟡 编排正确，整体不可达终态

- `\set ON_ERROR_STOP on` + `\ir` 相对包含，顺序：TABLE→SEQUENCE→TYPE→VIEW→TRIGGER→FUNCTION→PROCEDURE→PACKAGE→PACKAGE_BODY→SYNONYM→DATA。依赖拓扑合理（视图先于引用它的函数、包 SPEC 先于 BODY）。
- 但由于 ON_ERROR_STOP，实际执行会在 **VIEW/00_VIEW.sql（V_STUDENT_SCORE）** 处即中断；即使跳过，FUNCTION/PROCEDURE/PACKAGE_BODY 各有失败点。
- **结论**：脚本本身无需改；产物不过关导致一键安装不可用。

## 最终判定

- **可以直接使用（不改即投产）**：`TABLE/001_STUDENT_MST.sql`、`DATA/00_TEST_DATA.sql`（共 2 个）。
- **可安装但有语义差异，须人工复核后放行**：`SEQUENCE`、`SYNONYM`、`TABLE/002`、`PACKAGE`（仅作接口骨架）（共 4 个）。
- **不可直接使用，必须返工**：`TYPE`、`TRIGGER`、`VIEW`、`PROCEDURE`、`FUNCTION`、`PACKAGE_BODY`，以及依赖它们的一键脚本 `00_CREATE_ALL_PG.sql`（共 7 个）。
- 与官方验证结论一致（Gate 未通过、L3 24 个对象失败、L4 因无用例库被跳过）；本报告的增量发现是：**"安装成功"名单里仍有大量"首调即败"的对象（TRIGGER、F_GET_CONFIG_VALUE、FUNC_SETLOG 的 COMMIT、各 TODO 悬空调用），实际可用率显著低于 L3 表面通过率**。
- 一句话总结：perlstyle 规则引擎对**纯 DDL/数据类对象（TABLE/SEQUENCE/DATA/SYNONYM）已达到可用水平**，对**含嵌套子程序、集合、批量绑定、包状态、(+)外连接等 PL/SQL 高级特性的对象尚不具备自动等价迁移能力**，此类产物只能视为"待人工/AI 二次加工的半成品"。
