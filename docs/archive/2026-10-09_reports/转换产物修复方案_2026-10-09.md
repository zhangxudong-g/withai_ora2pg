# 转换产物不可用问题的解决方案

> 配套文档：《转换产物可用性逐一分析报告_2026-10-09.md》。本报告基于该分析发现的 A–H 八类问题，给出分层解决路线。**本文档仅为方案设计，未修改任何 SQL/代码。**

---

## 一、总体思路：三条路线组合

| 路线 | 适用场景 | 成本 | 收益 |
|------|----------|------|------|
| **R1 人工/AI 返工产物** | 让当前 oracle_poc/output 尽快可用（一次性 POC） | 中 | 快，但不可复制到下一个项目 |
| **R2 升级规则转换器** | 修 perlstyle 引擎的系统性缺陷 | 高 | 一次修复，所有后续项目受益 |
| **R3 AI Agent 二次转换** | 复杂 PL/SQL 语义级迁移 | 中高 | 项目已有基础设施，覆盖 R2 无法规则化的部分 |

推荐策略：**R1 先救火验证业务闭环 → R2/R3 治本**。因为 oracle_poc 本身是"测试转换工具的模拟系统"，产物缺陷大多是转换器通用缺陷的实例，只返工产物不修引擎，下个真实项目会原样复发。

## 二、按问题类别的解决方案（对应报告 A–H 归类）

### A. 嵌套子程序内联损坏（`x : IS NULL; /* INLINED */`、孤儿 `END 名称;`）
- **根因**：规则引擎把包内嵌套函数"就地内联"时只做文本替换，没有做语句边界识别，产生赋值残缺和悬挂 END。
- **R2 方案**：废弃纯文本内联；改为 AST 级重写——嵌套子程序一律提升为 schema 级独立 `CREATE FUNCTION`，调用点替换为函数名调用。项目里 `package_body_converter.py`（方案 C）已是这个思路，应把它接进 perlstyle 主流程替代内联逻辑。
- **R1 方案**：对 8 处损坏赋值 + 6 处孤儿 END 手工改写为独立函数。

### B. TODO 占位未实现（28 处 `/* TODO: complex body */`）
- **根因**：解析器识别不出复杂体，直接生成空壳桩。
- **R3 方案（首选）**：TODO 桩正是 AI Agent 的输入点。项目已有 `package_body_agent_integrator.py`（Rule-based 提结构 + AI Agent 转子程序），把带 TODO 的子程序连同其 Oracle 原文段落喂给 Agent 逐个生成 PG 实现，再经 L2/L3 验证回灌。
- **R1 方案**：POC 规模有限（PKG 共 12 个桩 + 8 函数 + 8 体内调用），可人工按 Oracle 源逐段翻译。

### C. Oracle 专有语法残留（BULK COLLECT/FORALL/%TYPE/%NOTFOUND/SQLCODE/UTL_FILE/PIPE ROW 等 60+ 处）
- **映射标准答案**（PG 等价写法，均为成熟模式，可直接写进规则表）：
  - `BULK COLLECT INTO t` → `SELECT ... INTO arr`（数组）或游标 FOR 循环
  - `FORALL i IN ...` → `FOREACH i IN ARRAY ...` 或 `EXECUTE format(...)` 批量
  - `%TYPE` → 具体类型，或用 `v_x student.name%TYPE`→ 规则引擎查表展开为 `varchar(n)`（需要 schema 元数据参与，可在 stage0 预处理器注入 DDL 字典）
  - `%NOTFOUND`/`%ISOPEN` → `GET DIAGNOSTICS cnt = ROW_COUNT` / PG 隐式游标天然无此问题（删掉判断即可）
  - `SQLCODE/SQLERRM` → `SQLSTATE` / `SQLERRM`（PG EXCEPTION handler 内置同名变量，多数场景仅需去掉 `SQL.` 前缀）
  - `PIPE ROW` → `RETURN QUERY` / `RETURNS SETOF`
  - `UTL_FILE` → `COPY ... TO PROGRAM` / `pg_write_file` 扩展 / 应用层导出（需业务决策）
  - `PRAGMA AUTONOMOUS_TRANSACTION` → 无直接等价，用 `dblink` 自治技巧或重构为调用方补偿逻辑（需业务确认）
- **R2 方案**：在 `pipeline/rules/` 按上述映射新增规则（rowtype.py、sql_exception.py 已存在，覆盖面不足，需扩展到 %NOTFOUND/%ISOPEN/SQLCODE/BULK COLLECT）。
- **注意**：这类是**机械可规则化**的，属于 R2 性价比最高的部分。

### D. `%SUBQUERY0%` 动态 SQL 占位符未回填（数据丢失级）
- **根因**：stage0 预处理器把动态 SQL 里的子查询抽成占位符，但生成后忘了回填。
- **R2 方案**：这是纯 bug——在 post_processor 增加"占位符必须归零"的断言：输出前扫描 `\%\w+%\`，非空即报错阻断，而不是静默产出坏 SQL。修复回填逻辑本身工作量小。
- **优先级最高**：它会静默丢数据，比语法错误更危险。

### E. PG 签名规则违反（INOUT/OUT 与 RETURNS 并存、函数体内 COMMIT）
- **R2 方案**：新增两条确定性规则：① 有 OUT/INOUT 参数且是函数 → 改用 `RETURNS TABLE`/`OUT` 参数形式之一，禁止混用；② 函数体内 COMMIT/ROLLBACK → 拆分为 PROCEDURE 或由调用方管理事务（标记需人工确认）。再加一条 L2 静态检查（类似现有 BEGIN/END 配平检查）：用 pglast 解析 CREATE FUNCTION 签名，检出非法组合提前报警。

### F. 类型/集合模型不等价（TABLE OF → array、`.EXTEND`、下标访问）
- **方案选择（需业务拍板）**：
  1. 数组方案：PL/SQL 原生支持 `arr[i]`、`array_length`，`.EXTEND`→`arr := array_append(arr, val)`，可完全规则化；
  2. pg_temp 临时表方案：更接近 Oracle 集合语义，但改动大。
  - 推荐 1（数组），并在 rules/array.py 中补齐 `.EXTEND/.DELETE/.COUNT` 方法映射——现有 array.py 显然未覆盖这些方法调用。

### G. (+) 外连接改写错误（连接条件丢失、JOIN 顺序错乱）
- **R2 方案**：rules/outer_join.py 存在但结果错。建议改为"AST 驱动"而非正则：先用 sqlglot/pglast 解析 SELECT，识别 WHERE 中带 `(+)` 的谓词，把对方表的谓词挂到 LEFT JOIN 的 ON 上，保留本表谓词在 WHERE。这是业界成熟做法，规则复杂度可控。
- **兜底**：L4 加"视图行数/抽样数据比对"用例（Oracle vs PG 同数据集跑 DIFF），防止改写"语法对但语义错"的漏网。

### H. 序列/同义词语义退化
- **方案**：属已知取舍，登记入差异清单即可。SEQ 同义词视图化后 NEXTVAL 失效 → 改为直接 `CREATE SYNONYM`（若目标库兼容）或在产物头部注释显式告警 + L2 加"引用视图取 NEXTVAL"检测。SEQUENCE MAXVALUE 截断/CYCLE 需在转换报告中列为"待业务确认项"而非静默处理。

## 三、工程保障层（防复发，无论选哪条路线都建议做）

1. **"可安装 ≠ 可用"的验证补强**：plpgsql 延迟解析导致 L3 通过但首调即败（TRIGGER、F_GET_CONFIG_VALUE 等）。建议在 L3 之后增加 **L3.5 冒烟执行层**：对每个 FUNCTION/TRIGGER 自动生成最小调用（`SELECT f(defaults...)`、触发器走一次 INSERT），捕获运行期异常。这能直接把本次报告发现的"潜伏炸弹"全部暴露出来。
2. **产物质量门禁**：转换输出前强制扫描禁用 token（`%TYPE`、`%SUBQUERY`、`/* TODO */`、`BULK COLLECT`、`SQLCODE`、`: IS NULL; /* INLINED */`），命中即降级为 draft 并计数入报告，禁止进入 `00_CREATE_ALL_PG.sql` 一键脚本。
3. **回归基线**：oracle_poc 就是为此存在的——把本次报告的逐对象判定做成期望清单（expected failures 列表），每次改规则后重跑 pipeline 对比，防止修 A 坏 B。

## 四、建议实施顺序

| 阶段 | 内容 | 产出 |
|------|------|------|
| P0（1–2 天） | 修 D（占位符断言+回填）、E 的静态检查、质量门禁 token 扫描 | 坏产物不再静默流出 |
| P1（3–5 天） | R2 规则补齐：C 类映射（%TYPE/SQLCODE/NOTFOUND/BULK COLLECT/PIPE ROW）、F 数组方法、A 的"提升为独立函数"改造 | PROCEDURE/FUNCTION/TRIGGER 语法级全通 |
| P2（3–5 天） | G 视图 (+) 改写 AST 化；R3 Agent 消化 28 个 TODO 桩 | VIEW/PACKAGE_BODY 可用 |
| P3（持续） | L3.5 冒烟执行层 + L4 数据比对用例库 | "首调即败"清零，Gate 可达标 |
| 并行 | R1：对当前 output 手工返工，先把 oracle_poc 业务闭环跑通 | POC 立即验证价值 |

**一句话结论**：不可用的根因集中在"纯文本规则引擎做了它做不了的语义级改写"。短靠人工返工产物、中靠补齐可规则化的 C/E/F 类映射与 D 类 bug、长靠 AI Agent 消化 TODO + AST 化改写 + L3.5 冒烟验证三道保险，才能让 Gate 从 86.6/B 走向真正可用。
