# 阶段 2：修复和完善脚本转换引擎

## 1. 阶段目标

将现有转换脚本改造成尽可能通用、可测试、可追踪的转换引擎，减少针对单个 SQL 或单个项目的硬编码。

## 2. 主要任务

### 2.1 梳理现有转换流程

确认当前脚本的完整处理链路：

- 输入文件和输入格式
- 编码识别与处理
- SQL / PL/SQL 分段
- 注释处理
- 语法识别
- 转换规则执行
- 输出文件生成
- 错误和警告记录

输出当前流程图和模块依赖关系。

### 2.2 识别当前转换缺陷

重点排查：

- Oracle 特有函数未转换
- 日期类型和日期函数差异
- 字符串连接差异
- NULL 处理差异
- ROWNUM 和分页差异
- (+) 外连接语法
- MERGE 语义差异
- 序列和自增列处理
- PL/SQL 变量声明
- 参数模式 IN / OUT / IN OUT
- 游标处理
- 动态 SQL
- 异常处理
- Package 依赖
- DBMS_SQL 调用
- 事务控制语句
- Oracle 类型和 PostgreSQL 类型映射

### 2.3 设计模块化规则体系

建议将转换逻辑拆分为独立规则模块：

- 数据类型转换规则
- 函数转换规则
- 运算符转换规则
- JOIN 转换规则
- 分页转换规则
- DML 转换规则
- PL/SQL 结构转换规则
- 游标转换规则
- 动态 SQL 转换规则
- 异常处理转换规则
- 系统包替代规则

每条规则应包含：

- 规则编号
- 适用条件
- 输入示例
- 输出示例
- 不适用场景
- 风险等级
- 是否需要人工确认

### 2.4 建立安全的转换策略

- 默认保留无法确认的原始内容。
- 不对不确定语义进行强制替换。
- 对高风险转换输出警告。
- 记录每次转换应用的规则。
- 记录无法转换的片段及上下文。
- 避免通过简单正则表达式破坏字符串、注释和嵌套结构。
- 对复杂 PL/SQL 使用分层解析或结构化处理。

### 2.5 增加转换前后检查

转换前：

- 检查文件编码。
- 检查括号和引号是否匹配。
- 识别 SQL 类型和 PL/SQL 对象类型。
- 收集依赖对象。
- 标记动态 SQL 和复杂语法。

转换后：

- 检查是否残留 Oracle 专用语法。
- 检查括号、引号和块结构。
- 检查函数和变量引用。
- 检查目标语法中的明显错误。
- 输出风险和待确认项。

### 2.6 建立回归测试

每次规则修改后自动执行：

- 基础 SQL 测试
- 复杂查询测试
- DML 测试
- Function / Procedure 测试
- 动态 SQL 测试
- 异常处理测试
- 负面测试和无法转换测试

记录：

- 输入版本
- 规则版本
- 输出差异
- 测试结果
- 是否引入回归问题

## 3. 主要产出

- 通用化转换引擎
- 模块化转换规则
- 转换前检查器
- 转换后检查器
- 转换警告和风险报告
- 自动化回归测试集
- 转换规则说明文档

## 4. 完成标准

- 新增案例时不需要修改大量核心代码。
- 无法确定的语义不会被静默改写。
- 所有高风险转换都有明确提示。
- 规则修改可以通过回归测试发现问题。
- 输出结果具备可追踪性和可审计性。
