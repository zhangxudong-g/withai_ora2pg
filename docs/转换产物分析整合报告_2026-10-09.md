## 一、判定标准（联合四层）

| 层 | 含义 | 当前覆盖 |
|---|------|----------|
| L1 静态 | 转换后文本的残留关键字、占位符、孤儿语法 | ✅ |
| L2 语法 | pglast 解析 | ✅ |
| L3 安装 | 真实 PG 沙箱执行 CREATE | ✅ |
| L3.5 冒烟 | 安装后**首调即测**（plpgsql 延迟解析盲区补丁）| ✅ 本轮补 |
| L4 行为 | 业务等价断言（输入/输出快照） | ❌ **当前完全缺失** |

**核心方法论**："能安装 ≠ 可用"——只看 L3 失败清单会系统性漏判延迟解析缺陷（%TYPE、INLINED 残骸、TODO 桩、SELF_xxx 伪标识符）。一律采用 **静态残留门禁 → L3 安装 → L3.5 首调冒烟 → L4 等价** 的四层联合判定。

### 2.3 真实 PG 8.4 沙箱首调冒烟（L3.5 新增，本轮实测）

| 对象 | 现象 | 正确值应为 | 原因 |
|------|------|-----------|------|
| `F_GET_TOTAL_SCORE(10001)` | 恒返 **-1** | 实际总分 | 嵌套函数 `VALIDATE_STUDENT_NO`/`BUILD_SQL` 整体丢弃 → WHEN OTHERS 回退 |
| `F_GET_GRADE_LEVEL(95)` | 恒返 **4** | 1（优秀） | 嵌套 `GET_THRESHOLD`/`DETERMINE_LEVEL` 整体丢弃 → WHEN OTHERS 回退 |
| `PKG.FUNC_FORMAT_DATE(20261009)` | 返 **`' '`（单空格）** | '2026-10-09' | 日期格式化转换丢失 |
| `PKG.FUNC_GET_GRADE_LEVEL(95)` | 恒返 **4** | 1 | `set_config` 阈值读取失败回退 |
| `PKG.FUNC_CALC_TOTAL(10001, NULL)` | 恒返 **0** | 实际总分 | 嵌套函数被丢弃 → WHEN OTHERS 回退 |
| `F_GET_JOBNUM()` | 恒返 **1**，序列不推进 | 递增批号 | `SEQ_JOBNUM.NEXTVAL FROM DUAL` 未转换 |
| `CALC_AVG(10001)` / `CALC_RANK(10001,3,1)` | 恒返 **0** | 实际平均/名次 | 同上 |
| `GET_STATUS_of_SCORE_RECORD()` | `column "self_score_record_is_pass" does not exist` | 方法返回值 | SELF.col 改写后未声明变量/未添加复合参数 |
| `PKG.F_GET_TOTAL(10001)` | `function func_calc_total(numeric, unknown) does not exist` | 桥接函数返回值 | 包内裸名跨函数调用需 search_path 含 `pkg_score_manage` |
| `SP_PROCESS_SCORE(...)` | `invalid transaction termination` | 过程正常执行 | 含 `COMMIT/ROLLBACK`（PG 8.4 不支持）|
| `INSERT INTO student_mst ...` | 触发器首调即报 `%TYPE` 解析失败 | 自动补 STATUS/DELETE_FLG | `STUDENT_MST.STUDENT_NO%TYPE` 残留 |

**关键认识**：在 141 个"L3 安装成功"对象中，**至少 10 个**对象会"装上即坏"，而 L3 完全无法发现。这是本次报告最重要的方法论贡献。

## 四、问题归类（A–H，定稿口径）

- **A 嵌套子程序文本内联损坏**（8 处 INLINED + 孤儿 END）→ 废弃内联，走 lift（T10）
- **B TODO 空壳桩**（28 处）→ AI Agent 二次转换 + validate_pg 硬校验回灌（T11）
- **C Oracle 专有语法残留**（%TYPE×5、BULK COLLECT/FORALL、PIPE ROW、UTL_FILE、SQLCODE 等）→ 规则补映射（T5）+ Agent 专项（T12）
- **D %SUBQUERY 占位符未回填**（3 处，静默丢数据，最高危）→ restore 兜底断言（T3）
- **E PG 签名/事务规则违反**（INOUT+RETURNS、函数内 COMMIT、`BEGIN set_config` 拼接、FROM DUAL）→ 确定性规则 + L2 静态检查（T12）

- **G (+) 外连接改写算法错误**（非残留而是改错）→ 结构化建图+拓扑排序（T4）★优先级上调
- **H 语义退化需业务确认**（GTT、MAXVALUE/CYCLE、SYNONYM→VIEW、UTL_FILE 去向）→ 登记《迁移注意事项》（T6）

## 五、根因诊断

### 5.1 为什么"装上即坏"普遍存在？

| 引擎行为 | 影响 |
|---------|------|
| plpgsql 函数体**延迟解析**（首次调用才完整解析/编译） | `CREATE FUNCTION` 不校验体内 SQL/列引用，所有 plpgsql 函数首调时炸弹不显形 |
| 文本级内联嵌套子程序 → 当源代码含复杂控制流时丢弃 | `x : IS NULL; /* INLINED */` 残骸 + 嵌套函数体 `/* TODO: complex body */` 注释 |
| 转换器占位符协议无回填校验 | `%SUBQUERY0%` 直接落产物；USING 子句残缺，MERGE 静默丢数据 |
| OBJECT TYPE MEMBER 方法直译为独立函数，未补复合类型参数 | `SELF.col` → `SELF_<type>_<col>`，变量未声明 |
| (+) 外连接改写为 JOIN 计划时，**条件归属按表名局部决策**而非按图论拓扑 | ON 子句挂错 JOIN；产生 `ON TRUE` 笛卡尔 LEFT JOIN |

### 5.2 为什么"安装失败率高"？

- 4 大缺能力：BULK COLLECT/FORALL、PIPE ROW、UTL_FILE、PRAGMA AUTONOMOUS_TRANSACTION（无 PG 8.4 等价物）
- 4 大规则漏洞：%TYPE 不查表展开、INLINED 残骸不修复、%SUBQUERY 不回填、(+) 改写不正确
- 1 大设计缺陷：PACKAGE 走"签名桩 + TODO"，对实现故障"无声兜底"，下游静默退化

### 5.3 为什么"分级评估会自相矛盾"？

- L3 只看"装上没装上"，无法识别"装上即坏"
- 旧快照（ISSUES P0-1/P0-3）已修复的项，新产物上确实消失（GROUP BY 字面量、NVARCHAR2[]、SYS_REFCURSOR 等）
- 但**新产物上出现了旧快照未覆盖的新缺陷**（如 SELF_xxx、INOUT+RETURNS 混用、%SUBQUERY 丢数据）

## 六、横向问题汇总

### A. 最危险：静默返回错误数据（L3 安装无法发现）

详见 §2.3 表。共 10 个对象"装上即坏"或"装上但静默给错值"，**纯安装级验证不可见**。

### B. Oracle 专有能力无 PG 8.4 等价物（需人工/架构方案）

| 能力 | 涉及对象 | 说明 |
|---|---|---|
| 自治事务 PRAGMA AUTONOMOUS_TRANSACTION + 包内 COMMIT/ROLLBACK | TRG_STUDENT_AU、FUNC_SETLOG、SP_*、P_* | PG 8.4 plpgsql 不支持事务语句（11+ 才支持）；需 dblink/pg_background |
| PIPELINED（PIPE ROW / RETURN ... USING BULK COLLECT） | F_GET_STUDENT_LIST_PIPELINE、F_GET_SCORE_LIST_PIPELINE | 需重写为 RETURNS SETOF + RETURN NEXT |
| 显式游标声明于存储过程 | SP_CALC_RANK、SP_GEN_SCORE_REPORT | PG 8.4 仅函数支持；需重写为 FOR ... LOOP 或改函数 |
| BULK COLLECT / FORALL | SP_BATCH_*、PROC_BATCH_* | 需逐条重写 |
| UTL_FILE | PROC_EXPORT_CSV | 无对应；需应用层落盘 |
| 复合触发器 | TRG_SCORE_COMPOUND | PG 无对应概念 |
| INSTEAD OF 于物化更新 | TRG_V_STUDENT_IO | PG 视图不支持，需触发器替代或换建模 |

### C. 转换完整性缺口（静默丢失）

- **5/6 触发器丢失**（00_TRIGGER.sql）——最严重的完整性缺口
- 包级 PIPELINE / 嵌套子程序"complex body"被丢弃为 `/* TODO: complex body */` 注释
- PIPELINE 相关嵌套函数被提升为裸全局函数，形成双套命名空间
- %SUBQUERY 占位符未回填（PROCEDURE 3 处）——静默丢数据

### D. 部署注意事项

1. **search_path 必须包含 `pkg_score_manage`**，否则包内裸名跨函数调用运行时失败
2. 临时表 TEMP_SCORE_BATCH 是会话级的，多会话批量共享场景需改为普通表或按会话使用
3. 触发器依赖安装顺序：先表 → 触发器 → 测试数据
4. 序列访问必须用 `nextval('...')`，不能沿用 `.NEXTVAL` 写法

## 七、修复策略总览

详见 `docs/改进任务书_达到可用状态_2026-10-09.md`。架构上把现有三条路线收敛为一个明确分工：

```
oracle_poc/01.SQL (Oracle 源)
   │
   ├─[规则直通区] perlstyle_engine ──► TABLE / SEQUENCE / DATA / 简单 VIEW      （已达标，保持）
   │        ▲ 仅修 3 个系统性 Bug：%SUBQUERY 回填(T3)、(+) ANSI JOIN(T4)、%TYPE 查表(T5)
   │
   ├─[AST 升级区] pipeline/parsers (ANTLR4, 需先装运行时 T7) ──► MigrationMetadata
   │        ├─ TRIGGER 重建（T8）
   │        └─ TYPE 对象类型→PG composite/函数/数组重设计（T9）
   │
   └─[AI Agent 区] pipeline/stages/stage3_ai ──► FUNCTION / PROCEDURE / PACKAGE_BODY 复杂体
            ├─ 嵌套子程序：禁用文本内联 → package_body_converter 提升为顶层函数（T10）
            ├─ TODO 桩：package_body_agent_integrator 喂给 Agent 逐段转换（T11）
            └─ BULK COLLECT/FORALL、PIPE ROW、UTL_FILE、自治事务：Agent 出方案 + 人工确认（T12）
```

**路由策略**：简单机械变换走规则（快、稳），语义级改写走 AST，识别不出/复杂体走 AI Agent（有验证回灌）。

## 八、验收建议

1. **可以交付/验收的部分**（结构层）：表、序列、视图、测试数据、同义词 + TRG_STUDENT_BI。
2. **不可验收、需返工的部分**（行为层）：FUNCTION 全量、PROCEDURE 全量、PACKAGE_BODY 12 个失败 + 已装对象的静默错误、TYPE 6 个方法函数、CREATE_ALL.sql。
3. **必须在交付前人工决策**：5 个丢失触发器的行为是否需要（建议：TRG_SCORE_BIU、TRG_SYSTEM_CONFIG_BD 属业务正确性，必须补）；UTL_FILE 去向；GTT 替代方案。
